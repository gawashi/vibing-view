<objective>
Build the free-tier detection engine: classify each FMP response as available / requires-plan / rate-limited, persist that per-timeframe verdict in a userData JSON cache (keyed by a hash of the API key, sticky for plan-gating, next-UTC-day expiry for rate-limits), clear it on key change, and expose the per-timeframe status map to the renderer over a new `capabilities.get()` IPC channel. This also makes `httpGetJson` surface the HTTP status + body on failure so the classifier can tell 403 from 429.

Purpose: DATA-04's detection layer. This is the engine every gated-UI surface (Plan 05) consumes.
Output: A tested classifier + cache + IPC channel; the renderer can ask "what's the status of each timeframe for this key?"

## Why this is a standalone (horizontal) plan

DATA-04's user-visible outcome (gated buttons + toast) is delivered in Plan 05. This plan is the shared engine underneath it. Splitting engine-from-UI here is a **context-cost** decision, not a difficulty judgment: engine + IPC + classifier/cache tests + the two gated-UI sub-slices together would exceed ~50% of one agent's context (~13 files). The engine is also irreducibly shared — both the requires-plan and rate-limited UIs consume the same classifier/cache, so it cannot be split vertically without duplicating it. Plan 04 (engine) → Plan 05 (UI) is the honest structure. Plan 04's outcome is verifiable via unit tests (classifier verdicts, cache expiry) even though it has no visual change on its own.

## Flagged Assumption (edge-probe unresolved for DATA-04)

DATA-04 was unclassified by the edge probe (Japanese text). Its edges are governed here by D-19 (auto-detect from response, cache the verdict), D-20 (rate-limit judged from the response, never a local counter), D-21 (lazy re-probe on key change), and DESIGN-ADDENDUM §7/§8. The §7 response-shape conditions are MEDIUM-confidence pending real-key verification — the classifier is the single tunable seam (marked `// ponytail:`). No silent drop.
